# 일반전 UX 개선 기록 (Issue #23)

## 변경 이유
- 한 판 종료 후 바로 다시 할 수 없고, 이전 샷마다 결과만 즉시 나타나서 실제 알까기처럼 느껴지지 않았습니다.
- 화면 좌우 여백을 활용하지 않고 턴별 탈락 수와 발사자 기록이 없었습니다.
- 기존 최대 세기 160은 충돌 순간의 속도와 이동량이 지나치게 컸습니다.

## 개선 내용
- **재대전:** 경기가 끝난 상태에서 두 참여자 각 1회 동의가 모이면 같은 방에 새 매치를 생성합니다.
  새 경기 생성은 방 행 잠금을 기준으로 직렬화해 중복 생성을 방지합니다. 기존 매치 및 샷은 삭제하거나 덮어쓰지 않습니다.
  첫 플레이어가 신청하면 1/2 준비로 보이고, 다른 플레이어의 재동의 시 2번째 경기가 생성됩니다.
- **턴 로그:** 각 샷의 `input.expectedBoard`와 `result_state`를 비교해 탈락 알을 소유자별로 집계합니다.
  턴 번호, 누가 쐈는지, 선공·후공 각 탈락 수를 게임판 우측 패널에 표시합니다.
  로그만 스크롤하고 화면 전체는 데스크톱 뷰포트에 맞춥니다. 모바일에서는 게임판 아래에 배치됩니다.
- **물리 모션:** 서버가 확정한 `simulateShotWithFrames` 이동 경로 일부(최대 100 프레임)를 `shots.input.frames`에 보관합니다.
  화면은 DB에 기록된 최신 샷의 프레임만 재생합니다. 프레임 종료 후 정본은 항상 `matches.board_state`입니다.
  페이지 재접속 시 오래된 샷을 강제로 재생하지 않고 서버 스냅샷을 보여 줍니다.
  `prefers-reduced-motion` 환경에서는 모션을 생략합니다.
- **세기 균형 (1차 조정):** 드래그 입력 크기 **8~125**, 초기 알 위치 선공 `x=175`, 후공 `x=625`, 물리 초기 속도 계수 `0.095`, 프레임 마찰 계수 `0.973`.
  초기 배치와 입력 제한은 서버와 UI에서 동일하게 적용되며 진행 중이던 이전 경기를 직접 수정하지 않습니다.
  수치는 실제 사용자 피드백에 따라 후속 조정할 수 있는 **1차 밸런스 값**이지 통계적 최적값이 아닙니다.

## 데이터/보안 경계
- `rematch_votes`는 RLS가 활성화되고 비로그인/로그인 사용자 모두 직접 접근할 수 없습니다.
- `request_casual_rematch` RPC는 서명된 `auth.uid()`로 방 참가자 여부를 검사하며, 경기 종료 상태에서만 수락합니다.
- 경기별 샷 기록은 기존 `shots.match_id` 외래키를 그대로 유지합니다.
- 보드·이동 궤적은 신뢰된 Next.js 서버 API에서만 확정됩니다. 클라이언트의 직접 점수 수정은 계속 차단합니다.
- DB 스키마 변경은 migration 004(재대전)와 005(첫 경기 초기 배치)입니다.

## 검증
```bash
npm ci
npm run check
```

권장 실제 테스트: A/B 다른 브라우저에서 발사 → 상대편 판에 동일한 모션 → 우측 로그 탈락 수 일치 → 경기 종료 → A만 다시하기(1/2) → B 동의 → 새로운 5대5 판 시작 → 이전 기록 보존 확인.
