# v0.3.0 — Omok 멀티게임 확장 아키텍처 (제안 / 미배포)

> 추적: Epic #217, Architecture #218, Engine #219, Database #220, PvP #221, AI #222, Ranked #223, UI/Release #224.
> 본 문서는 구현 계약의 초안입니다. **운영 데이터베이스나 Vercel 설정을 변경하지 않습니다.**

## 1. 범위와 출시 정의

- 현재 Alkkagi 물리 기반 알까기는 **전부 그대로 유지**합니다. 오목은 독립 게임 엔진·DB 상태·경기 화면을 갖습니다.
- v0.3.0 출시 목표: 오목 15×15 자유룰, 2인 일반전(코드/친구 초대), 서버 검증 착수·실시간 복구·채팅·기권·재대결, AI(난이도), 독립 랭크 RP 및 리더보드, 계정 XP 정책과 통합 로비.
- **규칙**: 흑 선공, 흑/백 교대, 가로·세로·양 대각선에 같은 돌 **5개 이상** 연속이면 승리. 3·3/4·4 금수 없음, 무르기 없음. 모두 차면 무승부. 렌주/교환룰은 이번 릴리스 범위에서 제외.
- 세부 기능은 서로 독립된 PR·테스트로 검증합니다. Release Candidate까지 기능 플래그로 비활성화할 수 있어야 합니다.

## 3. 제안 테이블 (실제 SQL은 #220에서 검증)

- `omok_rooms`: 방 ID/코드/host/status/TTL. `omok_room_players`: 참가자와 선·후공.
- `omok_matches`: match ID, room/AI/ranked 종류, black/white participant, status, board JSON 또는 정규화된 225칸, turn, version, winner, finished_at.
- `omok_moves`: match_id, turn, row/col, color/user, request_id(unique), committed_at. (match_id, turn) unique.
- `omok_ranked_queue`, `omok_ratings`, `omok_rating_history`는 #223 전용.
- XP는 기존 원장과 중복 지급 방지 전략을 검토한 뒤에만 연동. `source_kind` CHECK, 트리거 중복/획득량·일별 cap을 검증하며 기존 알까기 RP는 건드리지 않습니다.

### 트랜잭션/경합 계약

1. 서버는 인증 사용자·참가자 여부를 확인합니다. 클라이언트에서 보내는 `board_state`·`winner`·RP·XP는 신뢰하지 않습니다.
2. DB 트랜잭션은 매치 행 잠금, `status='active'`, 현재 `turn/version`, 당사자/돌 차례, `row,col` 범위와 빈 칸을 검증합니다.
3. 검증된 엔진으로 새 상태/승패 판정 후 `omok_moves` 기록과 매치 상태를 **한 트랜잭션**에서 확정합니다.
4. `request_id` 중복 재전송은 이중 착수를 만들지 않습니다. API는 성공 결과 또는 안정적인 conflict/idempotent 결과를 반환해야 합니다.
5. 중복·동시 착수·상대 턴·비회원·비참가자·종료 뒤 요청/인증 없는 읽기·쓰기 차단을 테스트합니다.
6. Realtime은 알림 수단이며 **DB 스냅샷이 최종 권위**입니다. 갱신 누락/재접속 시 안전하게 다시 조회합니다.

### 보안 체크

- RLS는 사용자 범위로, 게임 참가자만 경기/착수/채팅 데이터를 읽습니다.
- SECURITY DEFINER RPC는 `search_path=''`, 필요한 스키마 명시, 실행 권한 최소화, 항상 `auth.uid()` 검증.
- 서비스 키는 브라우저로 전달하지 않습니다. 착수 rate limit·방 생성/친구 초대 spam 제한을 유지합니다.
- 운영에 SQL을 적용하기 전에 **PG17 격리 DB**, 2계정 JWT/Realtime, 동시성·rollback/재실행 안전성 검증이 선행되어야 합니다.

## 4. 프론트엔드 경계

- 현행 `/lobby`와 알까기 `/rooms/*`·`/ranked/*` 링크/서버 Action 동작은 보존합니다.
- 오목 전용 경로 예시: `/omok`, `/omok/rooms/[id]`, `/omok/ranked`, `/omok/matches/[id]`. 구체적 URL은 #218의 프론트/시스템 담당 협의로 최종 확정합니다.
- 상단 게임 선택(알까기/오목) 이후 각 게임의 일반·랭크·AI 진입 카드 표시. 기존 UI 3D 구성·반응형·화면 밀도 유지.
- 오목 엔진과 UI/상태는 `src/lib/omok/*`·`src/components/omok/*` 아래에 격리합니다.
- 미출시 오목 UI는 **서버측 기본 OFF 기능 플래그** 뒤에 두고, 숨긴 경로에서도 서버/DB 권한 검사를 생략하지 않습니다.

## 5. 브랜치·PR·릴리스 경계

- 원칙: 기능 브랜치 → 작은 명확한 커밋 → `develop` 대상 Draft/일반 PR → 검토 및 CI 합격 후 병합.
- 예시: `docs/218-omok-v0.3-architecture`, `feat/219-omok-engine`, `feat/220-omok-db`, `feat/221-omok-pvp`, `feat/222-omok-ai`, `feat/223-omok-ranked`, `feat/224-omok-ui`.
- `release/v0.2.0`은 기존 Draft PR #207 기준의 별도 미완료 릴리스입니다. **0.3.0 작업을 0.2.0 RC에 포함하지 않습니다.**
- `release/v0.3.0`은 합격한 0.3 기능의 `develop` 통합 SHA를 동결한 이후에만 만듭니다. 패키지/잠금 파일 버전 정렬, CHANGELOG, 5종 릴리스 CI, PG17·Supabase E2E.
- Vercel 무료 한도 절감: 일반 PR의 자동 Preview를 강요하지 않고, 릴리스 후보에 대해서만 수동 Preview를 필요 최소 횟수로 사용.
- Vercel Preview ↔ Supabase Production 연결 여부·실제 DB 쓰기 범위·운영 적용 계획을 검토하고 사용자 승인 후 배포합니다.
- **사용자 승인 전 금지**: `main` 병합, Production/Preview 배포, 운영 Supabase SQL/DML 적용, 환경 변수 변경, tag/Release 발행.
- 사용자에게 로컬 저장소/.env가 없으므로 CI/PG17/가상 테스트와 배포 브라우저 2계정 E2E를 구분해 검증합니다.
