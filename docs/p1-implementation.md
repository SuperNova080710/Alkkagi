# P1 중간 점검 — 기술 구현과 확인 범위

## 구현 구조
- Issue #4 / #5: Next.js 16·Supabase Auth·PostgreSQL 기본 스키마와 RLS
- Issue #6: 인증된 사용자에 한해 초대 코드로 2인 방 생성·입장. 방 행 잠금으로 경쟁 입장을 처리하고, 대기방에서만 퇴장
- Issue #7: 800×500 보드, 양쪽 5개 알, 드래그 발사, 서버에서 결정적 충돌/마찰/이탈/승패 계산
- Issue #8: Next.js 서버 인증 후 소유권·턴 검증, 서버 비밀키 전용 RPC에서 행 잠금/턴 변경/샷 저장 원자화. 경쟁 요청은 DB 상태 비교로 차단
- Issue #9: Realtime 매치 변경 구독 및 4초 단위 스냅샷 폴링(이벤트 유실 시 복구); 두 브라우저 E2E는 실제 확인 필요

## 규칙
- 선공은 방장, 참가자는 후공입니다. 경기 중 알 5개씩 보유합니다.
- 자기 차례에 자신의 알만 드래그 발사할 수 있습니다. 드래그 5~160 화면 좌표만 허용됩니다.
- 서버는 물리 계산 후 확정된 스냅샷만 DB에 저장합니다. 브라우저에서 점수/상태를 직접 저장할 수 없습니다.
- 상대 알을 모두 제거하면 승리, 내 알이 모두 제거되면 패배, 양쪽 모두 0이면 무승부입니다.
- 경기 중 '기권'하면 상대방 승리로 종료합니다. 일반전 RP는 변하지 않습니다.
- 자동 턴 만료와 랭크전 기능은 P2/P3에서 추가합니다.

## 원격 적용 순서
1. 브랜치 PR의 CI가 통과했는지 확인합니다.
2. migration 202610280002 (초대방) → 202610280003 (경기) 순서로 동일 Supabase 프로젝트에 적용합니다.
3. Supabase Advisor에서 RLS/함수 권한을 재확인합니다.
4. Preview에서 두 실계정 A/B 방 생성→코드 참가→호스트 경기 시작→교대 발사→기권 또는 알 제거→승패와 DB 상태 일치를 검증합니다.
5. 최종 PR 병합 후 Production을 확인하고 ALEPH 제출 문구를 **실제로 확인한 동작만**으로 기록합니다.

## 보안
- 공개 Supabase 키는 인증된 RLS 조회에만 사용합니다.
- `SUPABASE_SECRET_KEY`는 서버 실행 환경에만 존재합니다. 브라우저 코드나 응답에 포함하지 않습니다.
- 서버가 Auth의 `getUser()`로 요청 주체를 검증합니다. RPC는 잠금 이후 턴·소유권·보드 스냅샷을 재확인합니다.
- 마이그레이션 내 `SECURITY DEFINER` 함수는 명시적으로 허용된 역할만 실행할 수 있습니다.
- 남은 과제: 레이트 제한·대규모 동시성·새로고침 시 UX·실제 두 기기 실측 테스트.
